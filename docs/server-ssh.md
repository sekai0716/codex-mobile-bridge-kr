# 고정 도메인 이름 · 자체 서버 + SSH

자체 서버에서 제공 HTTPS 입구, 컴퓨터가 자동으로 생성 SSH 역터널. 휴대폰 요청은 서버를 통해 컴퓨터 게이트웨이로 다시 돌아갑니다.，Codex 아직도 컴퓨터에서 실행 중。

**휴대폰 → 섬기는 사람 HTTPS → 섬기는 사람 `127.0.0.1:18787` → SSH 터널 → 컴퓨터 게이트웨이 `127.0.0.1:8787` → Codex App**

이 글은 일반 사용자를 대상으로 합니다. `try2love` 및 `https://codex.try2love.com` 이 예는 구성 데모용일 뿐이며 액세스 가능한 데모 사이트를 나타내지는 않습니다. 자신의 계정과 도메인 이름으로 바꾸십시오. 샘플 포트도 일치해야 합니다. App 의 설정。

**관리자 작업은 사용자 또는 서버 관리자가 수동으로 수행합니다.。App 수락하지 않음 sudo 비밀번호, 서버 소프트웨어 설치 없음, 서버 구성 또는 방화벽 수정 없음。** App 책임이 있는 SSH 로그인 확인, 전달 연결 유지 및 감지 HTTPS 입구. 서버 준비는 처음에만 수행하면 되며 일일 연결에는 필요하지 않습니다. sudo。

## 1. 도메인 이름 및 공용 네트워크 입구를 수동으로 준비

“모바일 접속 주소”완벽하게 채워질 수 있어요 HTTPS 도메인 이름은 비워둘 수도 있습니다. 도메인 이름을 사용하는 경우 서버 공용 네트워크에 대한 도메인 이름을 직접 확인해야 합니다. IP，도메인 이름을 구성합니다. HTTPS 인증서 및 역방향 프록시；App 도메인 이름은 자동으로 바인딩되지 않습니다.。

**공용 네트워크를 사용하려면 비워두세요. IP：** SSH 의“서버 주소”（별칭을 사용할 때 SSH 구성 중 `HostName`）공용 네트워크를 입력해야 합니다. IPv4 또는 IPv6；활성화된 구성을 저장한 후，App 자동완성 `https://공용 네트워크IP`，IPv6 대괄호를 자동으로 추가합니다. 공용 네트워크를 추측하기 위해 도메인 이름을 구문 분석하지 않습니다. IP；호스트 이름이나 인트라넷 주소를 사용하는 경우 구성된 전체 내용을 입력해야 합니다. HTTPS 접속주소。

공용 네트워크 IP 입구에는 여전히 서버 구성이 필요합니다 HTTPS 휴대폰과 컴퓨터에서 신뢰하는 리버스 프록시 Subject Alternative Name 이것을 포함한다 IP 유효한 인증서. 도메인 이름 인증서와 신뢰할 수 없는 자체 서명 인증서는 대체될 수 없습니다. 게이트웨이는 인증서 확인을 우회하거나 다음으로 다운그레이드되지 않습니다. HTTP。IP 계획에는 도메인 이름이 필요하지 않습니다 DNS，모바일 접속 443，SSH 루프백 전달이 아직입니다. `127.0.0.1:18787`。수출됨 IP 구성 참조에서는 사용자가 서버 자체에 인증서와 개인 키를 제공하고 갱신을 준비하도록 요구합니다. 인증서 개인키는 생성되거나 수집되지 않습니다.。

다음 DNS 및 Caddy 도메인 이름 인증서를 자동으로 신청하는 단계는 다음에 적용됩니다.**도메인 이름 입구**；IP 입구는 기존 에이전트를 우선적으로 재사용하고, IP 인증서 또는 사용 App 수출됨 IP 전용 구성 참조. 오직 SSH 계정을 자동으로 사용할 수 없습니다. HTTPS 입구。

도메인 이름에 DNS 관리하에 있을 것이다 `codex.try2love.com` 의 A 레코드는 서버 공용 네트워크를 가리킵니다. IPv4。서버에만 사용 가능한 공용 네트워크가 있습니다. IPv6 경우에만 설정 AAAA 기록. 아래에서 사용하세요 Caddy 기본 자동 HTTPS 해결책, 먼저 서버에 대한 직접 포인터를 사용하십시오 DNS 기록。

서버 방화벽 및 클라우드 플랫폼 보안 그룹에서 구성：

| 포트 | 사용 | 접근 범위 |
| --- | --- | --- |
| SSH 항구, 보통 22 | 컴퓨터가 서버에 적극적으로 로그인합니다. | 컴퓨터가 위치한 네트워크에 대한 액세스를 허용합니다. |
| TCP 80 / 443 | 인증서 확인、HTTP 점프 및 기본 HTTPS 입장 | 휴대폰 및 공인인증서 서비스 이용 가능 |
| 사용자 정의 HTTPS TCP 포트（예: 8443） | 휴대폰 주소가 포트를 명시적으로 지정할 때 사용됩니다. | 휴대폰 연결이 가능하며, 서버 방화벽 및 클라우드 보안 그룹에서 이를 허용해야 합니다. |
| 18787 | 서버 역방향 프록시 연결 SSH 터널 | 서버 루프백 주소만 공개되며 공용 네트워크에는 공개되지 않습니다. |

컴퓨터에는 공용 네트워크가 필요하지 않습니다. IP 또는 라우터 포트 포워딩을 하지만 서버에 연결할 수 있어야 합니다. SSH 포트. 캠퍼스 네트워크를 통해서만、VPN 또는 서버에 로그인하는 스프링보드라고 해서 휴대폰이 공용 네트워크에서 액세스할 수 있다는 의미는 아닙니다.。

## 2. 수동 준비 정상 SSH 사용자 및 전달 권한

공통을 선택하세요 SSH 다음과 같은 사용자 `try2love`，해당 사용자의 비밀번호, 개인 키를 사용하거나 SSH Agent。이 계정으로 로그인할 수 있는지 터미널에서 확인하세요. 일일 터널링에는 부여할 필요가 없습니다. sudo 권한이 있으며 일반 계정을 가입시킬 필요가 없습니다. Docker 관리그룹。

좋다 SSH 전달이 비활성화되었습니다. 관리자에게 확인을 요청하세요. SSH 서버 구성. 일반 사용자는 다음 구성 조각을 참조할 수 있습니다. 관리자는 기존 규칙을 결합하여 적절한 위치에 배치해야 하며 전체 구성 파일을 직접 덮어쓸 수는 없습니다.：

```text
Match User try2love
    AllowTcpForwarding remote
    GatewayPorts no
    PermitListen 127.0.0.1:18787
Match all
```

`PermitListen` 포트 입력이 일치해야 합니다. App 의“서버 루프백 포트”일관된；`GatewayPorts no` 항목 전달을 서버 내로 제한합니다. 관리자는 다른 사항도 확인해야 합니다. Match 규칙、`DisableForwarding` 규칙 충돌을 피하기 위해 공개 키 항목에 대한 제한。

관리자가 수정 후 먼저 사용해야 합니다. `sudo sshd -t` 서버 시스템의 서비스 관리 모드에 따라 구성을 확인하고 다시 로드하세요. SSH；기존 터미널을 유지하고 새로운 연결이 정상인지 확인 후 종료하세요. 서비스 이름은 시스템마다 다릅니다.，App 이러한 작업은 수행되지 않습니다. 참조하다 [OpenSSH 공식 구성 지침](https://man.openbsd.org/sshd_config#AllowTcpForwarding)。

## 3. 수동 구성 HTTPS 역방향 프록시

### 기존 웹사이트 또는 역방향 프록시

기존에 Caddy、Nginx 또는 패널에 독립 도메인 이름 사이트를 추가하고 역방향 프록시 업스트림을 입력하세요.：

```text
http://127.0.0.1:18787
```

원래 도메인 이름을 유지하세요 `Host` 헤더를 요청하고 응답 캐싱 및 스트리밍 응답 버퍼링을 끕니다. 기존 사이트를 덮어쓰거나 새 항목을 위해 사이트를 중지하지 마십시오. 인증서는 기존 역방향 프록시로 관리됩니다.。

### 아직 설치되지 않았습니다. HTTPS 제공하다

관리자가 누를 수 있음 [Caddy 공식 설치 튜토리얼](https://caddyserver.com/docs/install) 수동으로 설치하세요. 다음은 공식 Linux systemd 예시로 서비스。

관리자가 기존 구성을 엽니다.：

```sh
sudoedit /etc/caddy/Caddyfile
```

기존 사이트를 유지하고 이 독립 사이트 블록을 추가하세요.：

```caddyfile
codex.try2love.com {
    reverse_proxy 127.0.0.1:18787 {
        header_up Host {http.request.host}
        flush_interval -1
    }
}
```

관리자는 구성을 확인하고 성공 후 서비스를 다시 로드합니다.：

```sh
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
```

확인에 실패하면 새로고침을 수행하지 않고 먼저 오류를 수정하세요. 서비스가 아직 실행되지 않는 경우 공식 설치 및 서비스 튜토리얼에 따라 시작 상태를 확인하십시오.。DNS 네트워크 조건을 충족한 후，Caddy 자동으로 적용 및 갱신됩니다. HTTPS 자격증. 이때 컴퓨터 터널은 아직 연결되지 않았으며 액세스 도메인 이름이 표시될 수 있습니다. 502，그런 다음 연결을 시작하십시오.。

App 의“수동 구성 참조 내보내기”또한 사용 가능 Caddy 구성 및 선택 사항 Docker Compose 문서. 내보내기 및 복사는 참조 콘텐츠만 생성하고 해당 콘텐츠의 명령은 실행하지 않습니다.；Docker 설치, 컨테이너 시작 및 모든 관리자 작업은 사용자가 수동으로 수행합니다.。

내부 서버가 필요한 경우 Agent 현재 상황을 판단하는 데 도움을 주고, App 딸깍 하는 소리“복제 서버 확인 Prompt”。그것은 포함한다 HTTPS 주소, 포트 및 일반 사용자 정보, 요구 사항 Agent 읽기 전용으로 기존 서비스, 포트, 권한을 확인하고 실행하지 마세요. sudo、서비스를 설치하거나 수정하지 마십시오. 권한이 부족한 항목은 확인되지 않은 것으로 표시됩니다. 복제 자체가 서버에 연결되지 않음。

## 4. 에서 App 구성 저장 및 확인 SSH 로그인

에서“네트워크 및 로그인”다음에 추가“고정 도메인 이름 · 자체 서버 + SSH”，채우다：

- 휴대폰 접속 주소 : 본인 소유 완료 HTTPS 예를 들어 주소 `https://codex.try2love.com`；시작하려면 비워 두세요. SSH 구성 중인 공용 네트워크 IP 자동완성 HTTPS 주소, 인증서 요구 사항 섹션 참조 1 제전。
- SSH 인증 방법: 계정 비밀번호, 로컬 개인 키、SSH Agent 아니면 이미 SSH 별명。
- 서버 주소、SSH 포트 및 일반 사용자 이름: 로그인이 가능하도록 확인된 계정을 사용합니다.。
- 서버 루프백 포트: 기본값은 `18787`，역방향 프록시 및 전달 권한 설정과 일치해야 합니다.。

구성을 저장하고 클릭하세요.“조사하다 SSH 로그인”；아직 활성화되지 않은 구성도 확인할 수 있습니다. 준비가 되면 활성화를 선택하고 저장하세요. 처음 연결하는 경우 관리자가 제공한 서버 콘솔 또는 호스트 지문으로 확인해야 합니다.。

**확인을 통과하면 해당 계정에 로그인할 수 있다는 의미입니다.。** App 원격 명령을 실행하지 마십시오；DNS 확인에서는 도메인 이름이 올바른 서버를 가리키는지 여부가 아니라 도메인 이름을 확인할 수 있는지 여부만 확인합니다.。SSH 전달 권한, 인증서, 휴대폰 공중망 접속에 대한 추가 인증이 필요합니다.。

## 5. 연결을 시작하고 고정된 입구를 감지합니다.

딸깍 하는 소리“시작하다 SSH 연결”，App 컴퓨터 게이트웨이와 활성화된 모든 연결이 시작됩니다. 컴퓨터가 적극적으로 서버의 설정을 설정합니다. SSH 터널, 서버의 내부 포트 요청이 터널을 따라 컴퓨터 게이트웨이로 전달됩니다.。

확인하다 SSH 상태를 클릭한 다음“고정된 출입구 감지”。테스트에서는 로컬 컴퓨터를 다음과 비교합니다. HTTPS 주소에서 반환된 게이트웨이 인스턴스는 도메인 이름이 실제로 현재 게이트웨이에 연결되어 있음을 확인합니다. 감지 실패는 서버 설치 또는 구성 수정을 트리거하지 않습니다.。

마지막으로 전화기를 꺼라 Wi-Fi，셀룰러를 사용하여 자신의 도메인에 액세스하고, 로그인을 인증하고, 채팅 내용을 읽고, 동기화를 보내고 답장하세요.。

## 6. 일상적인 사용 및 문제 해결

동일한 공용 네트워크 IP 독립적인 HTTPS 포트는 여러 대의 컴퓨터를 연결합니다. Windows 사용 `https://공용 네트워크IP:8443`，Mac 사용 `https://공용 네트워크IP:9443`。각 컴퓨터에 대해 독립적인 서버 루프백 포트를 설정합니다（예: `18080`、`18081`），역방향 프록시는 각각 해당 포트로 전달하고 서버 방화벽 및 클라우드 플랫폼 인바운드 규칙에서 두 개의 공용 네트워크를 허용합니다. TCP 포트。IP 인증서는 공유할 수 있으며, 인증서 확인 및 갱신에 필요한 입장은 계속 유지됩니다. 각 컴퓨터는 그대로 유지됩니다 HTTPS 주소 및 로그인 설정。

브라우저 Cookie 호스트가 공유하고 각 호스트에게 전송됩니다. HTTPS 포트. 각 게이트웨이는 독립적으로 생성됩니다. Cookie 로그인을 구별하기 위한 이름입니다. 같은 IP 인터넷 서비스는 서로 신뢰할 수 있어야 합니다. 포트는 출입구 구별, 로그인 보호, 인증서 및 정확한 정보를 식별하는 데 사용됩니다. Origin 인증이 계속 적용됩니다.。

첫 번째 구성이 완료된 후에는 매일 게이트웨이만 시작하면 됩니다. 터널이 끊어지면 App 연결이 다시 시도됩니다. 게이트웨이를 중지하면 터널이 닫히고 HTTPS 서비스는 계속 이용 가능합니다. 컴퓨터, 게이트웨이 및 Codex App 온라인 상태를 유지해야 합니다. 컴퓨터가 종료되거나 최대 절전 모드인 경우 채팅에 액세스할 수 없습니다.。

| 현상 | 위치 확인 |
| --- | --- |
| SSH 로그인 실패 | 주소、SSH 포트, 사용자 이름, 인증 방법, 호스트 지문 및 네트워크 |
| 로그인에 성공했지만 전달에 실패했습니다. | 관리자 확인 SSH 전달 권한, 루프백 포트 점유 및 공개 키 제한 |
| 도메인 이름을 찾을 수 없거나 인증서 오류 | DNS 올바른 서버를 가리키고 있습니까？、80/443 도달 가능 여부 및 인증서 준비 여부 |
| HTTPS 보여주다 502 | 터널이 연결되어 있는지 여부 역방향 프록시 업스트림 포트는 다음과 같습니다. App 구성이 일관성이 있나요？ |
| 감지 결과 해당 입구가 현재 게이트웨이에 속하지 않는다는 메시지가 표시됩니다. | 도메인 사이트나 역방향 프록시가 다른 서비스를 가리키나요？ |
| 컴퓨터에서는 액세스할 수 있지만 휴대폰에서는 열 수 없습니다. | 공용 네트워크 액세스를 확인하려면 휴대전화의 셀룰러 네트워크를 사용하세요. 컴퓨터에서의 확인은 전화 확인을 대체할 수 없습니다. |
