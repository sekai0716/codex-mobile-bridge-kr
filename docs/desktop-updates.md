## 출시 과정

쪽으로 `main` 소스 코드를 병합하거나 푸시하면 테스트가 실행됩니다. CI，하지만 데스크톱이나 모바일용으로 자동으로 구축되지는 않습니다. App，업데이트는 출시되지 않습니다. 패키징이 필요한 경우 수동으로 실행 **Desktop builds** / **iOS unsigned build**，또는 출시 준비 후 아래의 버전 라벨링 프로세스를 따르세요. 소스 코드만 병합할 경우 버전 번호를 수정하거나 생성할 필요가 없습니다. tag。

1. 동기식 `package.json` / `package-lock.json`、Android/iOS 버전 및 증분 빌드 번호가 업데이트되었습니다. `RELEASE_NOTES.md`。기존 유지 Android 서명 및 모바일 애플리케이션 ID는 업그레이드를 덮어쓰는 대신 일시적으로 새 키를 생성할 수 없습니다.。
2. 창고 Actions Secret `UPDATE_SIGNING_KEY` 일치해야 함 `desktop/features/updates/update-public-key.pem` ～에 Ed25519 공개 키. 개인 키는 제출되거나 빌드 제품에 포함되지 않습니다. 업데이트된 기존 ID를 덮어쓰기 위해 공개 키를 다시 생성하지 마십시오.。
3. 소스 코드 테스트와 5개의 네이티브 실행 Desktop builds 목표：macOS arm64、macOS x64、Windows x64、Ubuntu x64、Ubuntu ARM64。Mac 게이트웨이 Electron 해당 아키텍처에서 runner 짓다; 설치, 아키텍처, 서명, 시작, 업데이트 핸드오버, 오류 복구 및 구성 보존을 확인합니다. 업그레이드 전 발급된 신뢰할 수 있는 휴대폰 바인딩 사용, 설치 교체 및 롤백 후 인증 재확인。iOS 재사용 가능한 빌드가 서명되지 않은 생성을 생성합니다. IPA 소스 코드 포함 ZIP；Android 원본 서명을 사용하여 로컬에서 생성 APK。
4. 푸시 매칭 버전 tag，또는 기존 버전의 경우 tag 수동으로 실행 **Prepare signed release draft**。프로세스는 버전 및 서명 ID를 확인하고 5개의 데스크탑 대상을 기다립니다. iOS 빌드, 항상 초안 생성, 공식 버전 자동 게시 안 함。
5. 모두 수집 13 설치/소스 코드 패키지: 두 가지 유형 Mac 의 DMG/ZIP、Windows Setup/ZIP、2종 Ubuntu 의 DEB/AppImage、Android APK、iOS IPA 소스 코드 포함 ZIP，게다가 `bridge-update.json`。달리다 `node scripts/release-assets.cjs verify <폴더> --write-checksums` 확인 및 생성 `SHA256SUMS.txt`。확인 파일에 이 내용이 포함되어 있습니다. 14 파일; 인증을 계속하려면 서명 페이로드를 업데이트하세요. macOS arm64/x64 및 Windows x64 3개 중 ZIP。
6. 업로드 누락 Android 패키지 및 최종 검증 파일을 만든 다음 초안의 모든 자산을 다운로드하고 실행합니다. `node scripts/release-assets.cjs verify <폴더>` 다시 확인하세요. 초안은 완전성, 서명 및 모든 계획 자산이 승인된 후에만 공식 버전으로 출시됩니다. 실패할 경우 초안은 검토를 위해 보관됩니다. 게시 후 실제 다운로드 주소를 확인하세요、Latest 및 App 업데이트 결과 확인。

`bridge-update.json` 시그니처 봉투예요：`payload` ～을 위한 JSON 원시 바이트 Base64，`signature` ～을 위한 Ed25519 징후. 페이로드에는 다음이 포함됩니다. schema、버전, 설명, 플랫폼 파일 이름, 크기 및 SHA-256。App 파일 정보는 내부 공개키 검증이 완료된 후에만 허용되며, 다운로드 주소는 본 창고로 고정됩니다. Release，다운그레이드 거부가 플랫폼과 일치하지 않습니다.。

## 설치 트랜잭션 및 복구

사적인 stdio 의 `update-prepare` 애플리케이션이 위치한 디렉토리에 생성 `.cmb-update-*`，패키지 확인 및 확장, 확인 macOS 런타임을 서명하고 빌드한 다음 이전 런타임을 독립 실행형 업데이트 프로세스로 복사합니다. 휴대폰 HTTP 인터페이스는 업데이트 작업을 제공하지 않습니다.。

`update-apply` 토하라 App 종료 후 디렉토리를 교체하고 새 버전을 기다립니다. App 필요한 경우 게이트웨이 로드를 확인하고 복원합니다. 실패 시 복원 시도 `previous` 그리고 원래 버전을 실행해 보세요。Windows ZIP 덮어쓰기 및 업데이트는 기존 제거 프로그램 및 바로 가기를 유지하고 현재 사용자에 대한 해당 제거 버전 정보를 업데이트합니다.。

업데이트 프로세스의 작업 디렉터리는 설치 디렉터리의 상위 디렉터리여야 합니다.。Windows 프로세스의 작업 디렉터리는 잠겨 있으며, 업데이트 프로그램 자체가 임시 디렉터리에 복사되더라도 여전히 작업 디렉터리로 사용하고 있는 이전 설치 디렉터리를 이동할 수 없습니다. 다시 시작한 후 문제를 방지하려면 작업 디렉터리를 트랜잭션 디렉터리로 설정하지 마세요. App 이를 상속받아 다음 업데이트 시 정리에 영향을 줍니다.。

1.1.0 업데이터 작업 디렉터리가 수정되었습니다. 이전에 게시됨 beta.7 및 1.0.0 이 작업 디렉터리가 설정되지 않았습니다. 설치 디렉터리에서 실행한 후 인앱 업데이트가 나타날 수 있습니다. `WinError 32` 그리고 원래 버전을 복원하세요. 이 경우 트레이에서 ”게이트웨이 중지 및 종료”를 선택한 후 대상 버전을 실행하십시오. Windows `Setup.exe`，원래 위치에 설치합니다. 먼저 게이트웨이 데이터를 제거하거나 삭제할 필요가 없습니다. 설치된 이전 버전은 업데이터 시작을 담당하므로 새 버전 다운로드 패키지를 출시하는 것만으로는 이 업데이트에 대한 이전 버전의 시작 동작이 수정되지 않습니다.。

업데이트 결과는 데이터 디렉터리에 있습니다. `desktop-update-result.json`，프로세스 로그를 다음으로 업데이트합니다. `desktop-update.log`。성공한 후에는 이전 애플리케이션의 복사본을 보관하고 다음 업데이트를 준비할 때 정리하세요. 실패한 트랜잭션 디렉터리는 복구를 위해 보관됩니다. 예상치 못한 정전, 디스크 손상 또는 권한 변경에는 여전히 수동 복구가 필요할 수 있습니다. `previous`。이러한 경우에는 백업을 삭제하지 마십시오。

자동 청소 전용 핸들 `plan.json` 데이터베이스의 대상 설치 경로와 일치하고, 분명히 성공했거나 복구된 트랜잭션만 삭제하는 트랜잭션입니다. 최종 결과 없이 보조 프로세스가 시작되었거나 디렉터리에 아직 확인되지 않은 복구가 있습니다. `previous` / `failed` , 후속 업데이트가 차단되고 전체 트랜잭션이 보존됩니다. 시간 초과 또는 프로세스 종료는 복구가 완료되었음을 증명하지 않습니다. 소유권을 알 수 없는 거래 및 기타 설치된 사본은 수정되지 않습니다.。
