CODEX MOBILE BRIDGECONNECTION GUIDE 개요로 돌아가기

SETUP / CONNECTIONS

모든 단계를 연결하세요.

연결 방법을 선택한 후 다이어그램과 단계를 따르세요. 각 단계에서는 작업할 위치, 필요한 권한 및 성공을 확인하는 방법을 설명합니다.

공개 다운로드는 v2.1.3(안정적)이며 아래의 기존 터널/역방향 프록시 옵션을 포함합니다. 원격 액세스를 설정하기 전에 데스크톱 클라이언트를 설치하고 로그인하세요.

LAN 동일한 네트워크에서 임시 HTTPS · 권장 서버 또는 도메인 없음 기존 터널/역방향 프록시 이미 신뢰할 수 있는 HTTPS URL가 있습니다. Tailscale · 고정 HTTPSHTTPS 수정, 서버 없음 Cloudflare 터널로 명명됨 · 고급 도메인, 서버 유지보수 불필요 자체 서버 + SSH · 고급 HTTPS 항목이 있는 공용 서버 NAS / 도커 · 고급 기존 NAS / HTTPS 프록시

귀하 또는 귀하의 관리자는 수동으로 서버 소프트웨어를 설치하고 SSH 및 방화벽을 구성합니다. 앱은 sudo 비밀번호를 허용하지 않습니다. 복사 버튼은 텍스트만 복사합니다. 그들은 결코 명령을 실행하지 않습니다.

LAN: 최단 경로로 시작

연결 가능한 동일한 네트워크에 있는 전화기와 업무용 컴퓨터의 경우.

01
업무용 컴퓨터 · 앱

업무용 컴퓨터에서 시작

Codex 앱을 엽니다. 네트워크 액세스에서 LAN 액세스를 활성화하고 사용하는 네트워크 인터페이스를 선택한 다음 게이트웨이를 저장하고 시작합니다.

확인: 앱에 http://192.168.1.10:8787.와 같은 LAN 주소가 표시됩니다.

02
전화 · 브라우저

연결 가능한 동일한 네트워크에 가입

앱에 표시된 주소를 열거나 로그인 QR 코드를 스캔하세요. 전화기에서 localhost 또는 127.0.0.1을 사용하지 마십시오. 이는 전화기를 참조합니다. 게스트 Wi-Fi, AP 격리 및 직장 네트워크 정책으로 인해 장치 간 액세스가 차단될 수 있습니다.

확인: 로그인하고 채팅을 로드한 다음 자신의 테스트 채팅에서 메시지를 보내 응답을 확인하세요.

임시 HTTPS: 서버 설정 없음

빠른 개인 액세스에 권장됩니다. 도메인이나 서버가 없고 최소한의 설정 단계만 거치면 됩니다. 현재 URL는 일반적으로 게이트웨이 및 터널 프로세스가 계속 실행 및 연결되어 있는 동안 계속 사용할 수 있습니다. Cloudflare는 영구 할당이나 가동 시간을 보장하지 않습니다. 주소 알림을 활성화하고 터널이 다시 생성될 때 새 URL를 수신하도록 알림 채널을 구성합니다. 전달은 연결 및 알림 서비스에 따라 달라집니다.

URL 변경이 허용될 때 원격 액세스를 시도하는 경우입니다.

01
업무용 컴퓨터 · 앱

임시 연결 추가

Codex 앱을 열고 임시 HTTPS · Cloudflare를 추가하고 활성화한 후 게이트웨이를 저장하고 시작하세요. cloudflared가 번들로 제공되는 패키지에는 추가 커넥터 설치가 필요하지 않습니다. 이전 패키지가 누락되었다고 보고하는 경우 먼저 런타임 설정에서 설치하십시오.

확인: 앱이 .trycloudflare.com 아래에 HTTPS 주소를 표시합니다.

02
전화 · 브라우저

모바일 데이터로 인증

Wi-Fi를 끄고 앱에서 현재 URL를 엽니다. 게이트웨이 자격 증명 또는 유효한 로그인 QR 코드를 사용하세요. 주소 알림은 변경된 후 새로운 URL를 찾는 데 도움이 됩니다.

확인: 로그인하고 모든 작업을 읽고 보냅니다. 게이트웨이가 중지되거나 컴퓨터가 절전 모드인 경우 항목을 사용할 수 없습니다.

안정적인 주소를 얻으려면 도메인을 임시 URL로 반복적으로 리디렉션하는 대신 명명된 Cloudflare 터널이나 자체 서버를 사용하세요.

Tailscale: 하나의 HTTPS 주소 유지

Tailscale 공용 전달 또는 릴레이 트래픽은 해외 노드를 통과할 수 있습니다. 중국 본토에서의 직접 액세스는 느리거나 시간 초과될 수 있습니다. 비공개 P2P 경로는 공개 유입 경로 액세스와 다릅니다.

서버, 도메인 구매 또는 초대가 필요하지 않습니다. 업무용 컴퓨터에 공식 클라이언트를 설치하고 게이트웨이에 연결하세요.

v2.0.0에서 사용 가능합니다. 게이트웨이 컴퓨터에 공식 Tailscale를 설치하고 로그인한 후 초기 서비스/퍼널 권한을 부여하세요.

02
업무용 컴퓨터 · 게이트웨이

고정 주소를 감지하고 저장합니다.

네트워크 액세스에서 고정 HTTPS · Tailscale를 추가하고 공개 액세스 · 퍼널을 선택한 후 저장합니다. Tailscale 감지를 클릭하고 URL를 읽은 후 다시 저장하세요. 게이트웨이 로그인을 활성화된 상태로 유지하세요. HTTPS 주소는 Tailscale에서 제공됩니다. DNS 레코드나 인증서 업로드가 필요하지 않습니다.

확인: 게이트웨이는 실제 .ts.net 주소를 표시합니다. 위의 예시 주소를 입력하지 마세요.

03
업무용 컴퓨터 · 게이트웨이 및 브라우저

최초 승인 시작 및 완료

게이트웨이를 시작하십시오. 승인이 요청되면 공식 페이지에서 Continue Tailscale 승인을 클릭하고 HTTPS / Funnel을 승인하세요. Tailscale 관리자가 이러한 기능을 활성화해야 할 수도 있습니다. 최초 공개 DNS 전파에는 최대 10분이 걸릴 수 있습니다.

기본적으로 포트 443을 사용합니다. 다른 Tailscale 서비스가 이를 소유한 경우 8443 또는 10000을 선택한 다음 감지하고 다시 저장하십시오. 게이트웨이는 기존 서비스를 덮어쓰거나 Tailscale에서 로그아웃하지 않습니다.

04
전화 · 브라우저 또는 앱

셀룰러 데이터로 확인

게이트웨이의 고정 항목을 확인한 다음 페어링 코드를 스캔하거나 휴대폰에서 로그인하세요. Funnel을 테스트할 때는 Wi-Fi를 끄고 Tailscale 전화 연결을 끊으므로 테스트에서는 공개 경로를 사용합니다. 채팅 로드, 전송, 다운로드 및 다시 연결을 확인합니다.

정상적으로 다시 시작한 후에도 주소를 유지하려면 동일한 장치 ID와 이름을 유지하세요. 장치 이름을 바꾸거나 제거하거나 계정을 변경하려면 다시 감지하고 저장해야 합니다.

컴퓨터는 활성 상태를 유지해야 하며 게이트웨이는 계속 실행되어야 합니다. Funnel에는 대역폭 제한이 있으며 중국 본토 네트워크의 액세스 속도를 보장하지 않습니다. 셀룰러 데이터와 Wi-Fi를 모두 확인하세요. 내장된 HTTPS 항목은 자신의 도메인이 아닌 .ts.net을 사용합니다.

비공개 대안: 비공개 네트워크 · 서비스를 선택하세요. 동일한 Tailscale 네트워크에 연결된 승인된 장치만 방문할 수 있습니다. 모바일 앱에는 내장 Tailscale 클라이언트가 포함되어 있지 않습니다.

공식 서비스 안내 ↗

Cloudflare 터널이라는 이름: 도메인이면 충분합니다.

Cloudflare 터널 트래픽은 해외 노드를 통과할 수 있습니다. 중국 본토에서의 직접 액세스는 느리거나 시간 초과될 수 있습니다. 네트워크에 따라 안정적인 프록시 경로가 도움이 될 수 있습니다.

고급 설정에는 DNS, HTTPS, SSH, 서버 또는 NAS 관리에 대한 관련 지식이 필요합니다. 명령 및 구성은 참조용일 뿐이며 사용자 환경에 적합하지 않을 수 있습니다. 사용하기 전에 이를 검토하고 데이터를 백업하고 필요한 승인을 얻으십시오. 귀하는 이러한 예제를 사용, 수정 또는 실행하는 데 따른 위험을 감수합니다. 해당 법률이 허용하는 최대 범위 내에서 작성자와 기여자는 합법적으로 제외되거나 제한될 수 없는 책임을 제외하고 결과적인 데이터 손실, 서비스 중단, 보안 사고, 비용 또는 기타 손실에 대해 책임을 지지 않습니다.

아래 단계에서는 v2.0.0 게이트웨이를 사용합니다. 연결을 활성화하기 전에 서버와 HTTPS 엔드포인트를 준비하세요.

자신의 도메인, Cloudflare 계정 및 온라인 업무 컴퓨터가 필요합니다.

모든 도메인, IP 및 사용자 이름은 예시입니다. 이를 자신의 값으로 바꾸십시오. try2love.com은 호스팅된 데모가 아닙니다.

01
Cloudflare 및 등록 기관 웹사이트

도메인을 Cloudflare DNS에 연결하세요.

Cloudflare에 도메인을 추가하고 적합한 계획을 선택한 후 기존 웹사이트와 메일 DNS 기록을 검토하세요. 할당된 두 개의 네임서버를 복사합니다. 도메인 등록기관에서 도메인 이름 서버를 이 두 주소로 바꾸세요.

두 개의 일반 A 레코드가 아닌 도메인 네임서버를 변경하세요. 등록기관에서 도메인을 갱신하세요. 활성화되면 Cloudflare의 DNS 레코드를 관리합니다.

확인: Cloudflare가 활성을 표시합니다. 보류 중인 경우 공식 마이그레이션 가이드를 참조하여 네임서버 철자와 이전 DNSSEC 설정을 확인하세요.

공식: 도메인 및 네임서버 설정 ↗
02
Cloudflare 웹사이트

명명된 터널을 만들고 해당 토큰을 복사합니다.

터널을 열고 Cloudflared 터널을 생성한 후 이름을 지정하고 커넥터 설치 명령을 검사하세요. 일반적으로 --token 다음의 긴 값인 터널 토큰만 복사합니다. API 키나 전체 명령이 아닙니다. 공개 페이지나 스크린샷에 포함하지 마세요.

번들 커넥터가 있는 앱은 터널을 실행합니다. 해당 설치 명령을 실행할 필요가 없습니다.

확인: 이 터널에 대한 토큰이 있고 앱에 저장할 준비가 되었습니다.

04
Cloudflare · 터널 노선

호스트 이름을 로컬 게이트웨이로 라우팅합니다.

이 터널의 경로/게시된 애플리케이션/공개 호스트 이름 페이지에 게시된 애플리케이션을 추가합니다. 라벨은 대시보드 버전에 따라 다릅니다. 호스트 이름에서 서비스로의 경로를 만듭니다.

경로 필드 예
하위 도메인 사본
도메인 try2love.com
길 비워두세요
서비스 유형 HTTP
서비스 URL 로컬호스트:8787

서비스 URL 상자가 하나 있으면 http://localhost:8787.를 입력합니다. 게이트웨이의 청취 포트를 일치시킵니다. 전화기의 HTTPS URL를 입력하거나 A 레코드를 컴퓨터의 LAN IP에 지정하지 마십시오.

확인: 저장하면 터널에 대한 DNS 레코드가 생성됩니다. 상충되는 기록을 변경하기 전에 검사하십시오. 다른 사이트를 덮어쓰지 마십시오.

05
Cloudflare · 규칙

HTTP를 HTTPS로 리디렉션

도메인의 규칙 → 개요 → 규칙 생성 → 리디렉션 규칙을 열고 사용자 정의 필터 표현식을 선택합니다. 이는 게이트웨이 호스트 이름과만 일치합니다. 예제 도메인을 교체하세요.

(http.request.full_uri wildcard r"http://codex.try2love.com/*")

아래 표현식, 상태 301 및 쿼리 문자열 보존을 사용하여 동적 URL 리디렉션을 선택합니다. 유효성 검사가 성공한 후 배포합니다.

concat("https://codex.try2love.com", http.request.uri.path)

확인: http://codex.try2love.com를 열면 로그인이 표시되기 전에 HTTPS로 업그레이드됩니다. 이전 HTTP 로그인 페이지를 다시 엽니다.

06
업무용 컴퓨터와 전화

게이트웨이 및 전화 액세스 확인

앱에서 수정된 항목 확인을 선택합니다. 휴대폰 Wi-Fi를 끄고 모바일 데이터를 통해 도메인을 엽니다. Cloudflare 또는 SSH 비밀번호가 아닌 게이트웨이 자격 증명으로 로그인하세요.

확인: 항목 확인이 통과되고 휴대폰에서 로그인하고, 채팅을 읽고, 답장을 보내고 받을 수 있습니다.

자체 서버 + SSH: 단계별로 서버 준비

고급 설정에는 DNS, HTTPS, SSH, 서버 또는 NAS 관리에 대한 관련 지식이 필요합니다. 명령 및 구성은 참조용일 뿐이며 사용자 환경에 적합하지 않을 수 있습니다. 사용하기 전에 이를 검토하고 데이터를 백업하고 필요한 승인을 얻으십시오. 귀하는 이러한 예제를 사용, 수정 또는 실행하는 데 따른 위험을 감수합니다. 해당 법률이 허용하는 최대 범위 내에서 작성자와 기여자는 합법적으로 제외되거나 제한될 수 없는 책임을 제외하고 결과적인 데이터 손실, 서비스 중단, 보안 사고, 비용 또는 기타 손실에 대해 책임을 지지 않습니다.

아래 단계에서는 v2.0.0 게이트웨이를 사용합니다. 연결을 활성화하기 전에 서버와 HTTPS 엔드포인트를 준비하세요.

공용 서버는 HTTPS를 제공합니다. 업무용 컴퓨터가 복귀 터널을 시작합니다.

서버는 HTTPS 및 전달을 처리합니다. Codex 및 게이트웨이는 업무용 컴퓨터에서 실행됩니다. 서버를 한 번 준비한 다음 일상적인 사용을 위해 컴퓨터 게이트웨이를 시작합니다.

모든 도메인, IP 및 사용자 이름은 예시입니다. 이를 자신의 값으로 바꾸십시오. try2love.com은 호스팅된 데모가 아닙니다.

전화 URL는 선택 사항입니다. 도메인의 경우 DNS가 공용 IP 서버를 가리키도록 하고 HTTPS를 구성합니다. SSH 서버 주소(또는 별칭 HostName)의 공개 IP를 사용하려면 공백으로 두십시오. 저장하면 https://public-IP.가 채워집니다. 서버에는 여전히 역방향 프록시와 해당 IP가 포함된 주체 대체 이름의 신뢰할 수 있는 인증서가 필요합니다. SSH만으로는 충분하지 않습니다.

기존 SSH 방법 또는 클라우드 콘솔을 사용하여 로그인합니다. 이 명령은 서비스를 변경하지 않고 OS 및 수신 대기 포트를 검사합니다.

cat /etc/os-release

Ubuntu/Debian에서는 아래의 적절한 경로를 사용하세요. :80 또는 :443이 수신 중이거나 Nginx 또는 Caddy 패널을 사용하는 경우 기존 사이트 경로를 선택하고 두 번째 웹 서버를 시작하지 마십시오. 빈 명령 결과는 프로그램이 없음을 의미할 수 있습니다. 권한 제한 검사를 확인되지 않은 것으로 표시합니다.

서버에 공개적으로 접근할 수 없거나 확실하지 않습니다.

클라우드 콘솔에서 공개 주소와 인바운드 규칙을 확인하세요. 캠퍼스 네트워킹 또는 VPN를 통해서만 연결할 수 있는 개인 서버는 SSH가 작동한다고 해서 자동으로 공중 전화 통화가 되지 않습니다. 공개 HTTPS 항목을 요청하거나 명명된 Cloudflare 터널을 사용하세요.

DNS가 실제로 호스팅되는 레코드를 추가합니다. 네임서버가 Cloudflare로 이동한 경우 등록 기관의 이전 DNS 영역이 아닌 Cloudflare DNS를 편집하세요.

서버에 공용 IPv6이 작동하는 경우에만 AAAA를 추가하세요. 이 호스트 이름이 이미 Cloudflare 터널을 제공하는 경우 먼저 새 호스트 이름에서 서버 설정을 테스트하세요. DNS를 127.0.0.1 또는 컴퓨터의 192.168.x.x 주소로 지정하지 마십시오.

nslookup codex.try2love.com

확인: 작업 컴퓨터에서 nslookup을 실행합니다. 서버 공개 IP를 반환해야 합니다. 캐시된 DNS 결과를 업데이트하는 데 시간이 걸릴 수 있습니다.

Ubuntu가 UFW를 사용하면 어떻게 되나요?

관리자에게 먼저 상태를 검사하도록 하세요. UFW가 이미 활성화된 경우에만 웹 포트 규칙을 추가하세요. 이 가이드에 대한 방화벽을 활성화/재설정하거나 SSH 액세스를 제거하지 마세요. 클라우드 보안 그룹은 별도로 구성됩니다.

sudo ufw status verbose

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

방화벽d, 클라우드 방화벽, 패널 방화벽의 경우 관리자에게 기존 시스템을 사용하여 동등한 규칙을 추가하도록 요청하세요. 관리 서버가 공용 80/443을 노출할 수 없는 경우 프로비저닝된 다른 HTTPS 항목을 요청하십시오.

확인: 클라우드 및 호스트 방화벽 규칙을 모두 확인합니다. 여전히 실행 중인 HTTPS 서비스와 외부 테스트가 필요합니다.

04
업무용 컴퓨터 + 서버 관리자

일반 SSH 사용자 준비

로그인이 가능한 기존 일반 계정을 재사용하세요. 전용 계정이나 sudo 접속이 필요하지 않습니다. 업무용 컴퓨터 터미널에서 로그인을 확인한 후 앱을 종료하고 구성하세요. 서버 콘솔 또는 관리자 값과 비교하여 첫 번째 호스트 지문을 확인합니다.

ssh -p 22 try2love@203.0.113.10
루트만 사용할 수 있습니다. 일반 사용자는 어떻게 준비합니까?

Ubuntu/Debian 관리자는 아래 계정을 만들고 비밀번호 프롬프트를 따를 수 있습니다. 이는 sudo 액세스 권한을 부여하지 않습니다. 설정을 더 쉽게 하기 위해 SSH 비밀번호 인증을 전역적으로 활성화하지 마십시오.

sudo adduser try2love

비밀번호 로그인이 이미 허용된 경우 이 일반 계정을 확인하세요. 키 전용 서버의 경우 다음에 설명된 대로 공개 키를 설치합니다. 다른 시스템에서는 OS 관련 계정 관리 프로세스를 사용합니다.

서버에는 SSH 키가 필요합니다

작동 중인 키가 있으면 재사용하세요. 키를 생성하려면 업무 컴퓨터에서 ssh-keygen을 실행하고 기존 키를 덮어쓰지 않도록 새 파일 이름을 선택하세요. 암호를 사용하는 것이 좋습니다.

ssh-keygen -t ed25519

생성된 .pub 공개 키를 관리자에게 제공하여 사용자의 ~/.ssh/authorized_keys에 추가하세요. 개인 키를 업무 컴퓨터에 보관하세요. 아래 예에서는 Ubuntu/Debian의 기본 /home/try2love home을 가정합니다. 기존 파일에 추가하고 덮어쓰지 마십시오.

sudo install -d -m 700 -o try2love -g try2love /home/try2love/.ssh
sudoedit /home/try2love/.ssh/authorized_keys
sudo chown try2love:try2love /home/try2love/.ssh/authorized_keys
sudo chmod 600 /home/try2love/.ssh/authorized_keys

앱에서 로컬 개인 키를 선택하고 .pub 접미사가 없는 파일을 선택합니다. 설정된 경우 암호를 입력하세요. 개인 키와 비밀번호를 공개 구성 및 스크린샷에 포함하지 마세요.

확인: 회사 컴퓨터가 일반 사용자로 로그인할 수 있습니다. 서버 SSH 비밀번호와 전화 게이트웨이 비밀번호는 별도의 자격 증명입니다.

05
서버 · 관리자 확인 및 구성

이 사용자가 역방향 터널을 생성하도록 허용

적합한 경우 기존 전달 권한을 재사용합니다. 변경이 필요한 경우 관리자가 sshd_config, 포함된 파일, 일치 조건 및 공개 키 제한 사항을 검토한 후 아래에서 대상 사용자의 규칙을 추가하거나 조정하도록 합니다. 전체 SSH 구성을 교체하지 마십시오.

Match User try2love
    AllowTcpForwarding remote
    GatewayPorts no
    PermitListen 127.0.0.1:18787
Match all

AllowTcpForwarding 원격은 역방향 전달을 허용하고 PermitListen은 수신 주소를 제한하며 GatewayPorts는 수신기를 루프백 상태로 유지하지 않습니다. DisableForwarding 예, Authorized_keys의 이전 일치 규칙 또는 제한/포트 전달 없음은 여전히 ​​전달을 차단할 수 있습니다.

sudo sshd -t

구문 유효성 검사가 코드 0으로 종료되고 출력이 없는 경우에만 계속합니다. Ubuntu/Debian은 일반적으로 아래 ssh 서비스를 사용합니다. 다른 시스템의 서비스 이름을 확인하십시오. 기존 SSH 터미널을 열어두고 다른 터미널에서 새로 로그인했는지 확인하세요.

sudo systemctl reload ssh

확인: 새 단말기가 로그인할 수 있습니다. 실제 전달은 7단계에서 앱 터널을 시작한 후 확인됩니다.

서버 또는 제어판 · 관리자

HTTPS 구성: 상황을 선택하세요.

하나의 경로를 선택하십시오. 업스트림은 항상 업무 컴퓨터의 LAN IP가 아니라 SSH 서버 자체의 http://127.0.0.1:18787입니다.

A · 새로운 우분투/데비안, 기존 웹사이트 없음

포트 80/443이 다른 서비스에서 사용되지 않고 Caddy가 설치되지 않았는지 확인하십시오. 관리자는 공식 저장소에서 설치합니다. 계속하기 전에 한 번에 하나의 명령을 실행하고 오류를 해결하십시오. 패키지는 시스템 서비스를 생성하고 시작합니다.

sudo apt update
sudo apt install --yes debian-keyring debian-archive-keyring apt-transport-https curl gnupg
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/gpg.key | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo chmod o+r /usr/share/keyrings/caddy-stable-archive-keyring.gpg
sudo chmod o+r /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install caddy

Caddyfile을 백업하고 편집하세요. 예제 도메인을 교체합니다. 새로 설치하는 경우 샘플 :80 사이트를 아래 블록으로 바꿉니다. 실제 사이트가 이미 존재하는 경우 경로 B를 사용합니다.

sudo cp -a /etc/caddy/Caddyfile /etc/caddy/Caddyfile.before-codex-$(date +%Y%m%d%H%M%S)
sudoedit /etc/caddy/Caddyfile

codex.try2love.com {
    reverse_proxy 127.0.0.1:18787 {
        header_up Host {http.request.host}
        flush_interval -1
    }
}

sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy
systemctl is-active caddy

검증이 성공한 후에만 다시 로드하십시오. 마지막 명령은 활성으로 표시되어야 합니다. 캐디는 인증서를 획득 및 갱신하고 HTTP를 HTTPS로 리디렉션합니다.

공식 설치 지침 ↗
B · 기존 Caddy 또는 Nginx 웹사이트

구성을 백업하고 게이트웨이에 대한 전용 호스트 이름을 추가합니다. 기존 사이트를 덮어쓰거나 웹 서버를 중지하지 마십시오.

기존 캐디

이 블록을 활성 Caddyfile 또는 가져온 사이트 파일에 추가합니다. 다른 사이트를 보존하고 동일한 호스트 이름에 대한 중복 정의를 피하십시오.

codex.try2love.com {
    reverse_proxy 127.0.0.1:18787 {
        header_up Host {http.request.host}
        flush_interval -1
    }
}

sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl reload caddy

기존 Nginx

먼저 유효한 인증서를 프로비저닝하고 기존 인증서 도구 또는 패널을 사용하여 게이트웨이 호스트 이름에 대해 HTTP에서 HTTPS로 리디렉션합니다. 이 위치를 해당 호스트 이름의 HTTPS 서버 블록 안에 넣으세요. 위치 /가 존재하는 경우 해당 사이트의 블록을 복제하기보다는 편집하세요. 이는 인증서를 발급하지 않으며 완전한 Nginx 구성 파일이 아닙니다.

location / {
    proxy_pass http://127.0.0.1:18787;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}

sudo nginx -t
sudo systemctl reload nginx

nginx -t가 성공한 후에만 다시 로드하세요. 패널이나 컨테이너가 프록시를 관리하는 경우 다른 시스템 서비스를 만드는 대신 기존 구성 및 다시 로드 컨트롤을 사용하세요.

C · 웹사이트 제어판

기존 패널에 전용 호스트 이름 사이트 또는 역방향 프록시 항목을 만들고 다른 사이트를 보존합니다. 메뉴 라벨은 패널 버전에 따라 다릅니다. 아래 필드를 매핑하세요.

패널 프록시가 컨테이너에서 실행되는 경우 127.0.0.1은 해당 컨테이너를 참조하며 반드시 SSH 호스트일 필요는 없습니다. 관리자에게 네트워크 네임스페이스와 안전하게 연결 가능한 업스트림을 확인하도록 하세요. 포트 18787을 공개적으로 노출하지 마십시오.

D · 기타 OS, Docker 또는 관리자 액세스 권한 없음

다른 Linux 시스템의 경우 공식 캐디 가이드에서 일치하는 패키지 관리자를 선택하세요. 호스트 이름, 업스트림 및 확인은 동일하게 유지됩니다. Rocky/AlmaLinux에 apt 명령을 복사하지 마십시오. Windows 서버에는 관리자가 제공한 동등한 SSH 및 HTTPS 서비스가 필요합니다. 이러한 Linux 명령은 적용되지 않습니다.

기존 Linux Docker 엔진을 사용하면 앱에서 내보낸 수동 참조에 선택적 Caddy Compose 설정이 포함됩니다. 80/443이 비어 있을 때만 시작하고 인증서 볼륨을 유지하십시오. SSH와 동일한 Linux 호스트에서 호스트 네트워킹을 사용합니다. Docker는 관리자 권한을 우회하지 않습니다.

관리자 액세스 권한이 없으면 관리자에게 2~6단계를 제공합니다. sudo가 아닌 일반 SSH 계정과 허용된 전달 포트만 필요합니다. 앱의 복사 서버 검사 프롬프트를 사용하면 서버 측 에이전트가 읽기 전용으로 검사할 수 있습니다. 관리 권한은 부여되지 않습니다.

OS에 대한 캐디 설치 지침을 선택하세요 ↗

확인: HTTPS 인증서가 유효하고 HTTP가 HTTPS로 리디렉션됩니다. 터널이 시작되기 전에 502가 발생할 수 있습니다. 계속하기 전에 인증서 오류나 관련 없는 사이트를 수정하세요.

curl --max-time 10 -H 'Host: codex.try2love.com' http://127.0.0.1:18787/api/auth

인증된 필드와 기타 필드가 포함된 JSON가 필요합니다. 그런 다음 앱에서 고정 항목 확인을 선택하여 공용 HTTPS 인스턴스를 로컬 게이트웨이와 비교합니다. 마지막으로 로그인, 채팅 로딩 및 전화 모바일 데이터 전송을 확인합니다.

확인: 세 개의 레이어가 모두 통과됩니다. 일일 작업에는 sudo가 필요하지 않습니다. 컴퓨터를 깨어 있고 온라인 상태로 유지하십시오. 게이트웨이는 SSH 연결을 유지하고 재시도합니다.

01
터널 또는 프록시

이 컴퓨터의 실제 루프백 포트로 전달

게이트웨이가 실제로 포트 8787을 사용하는 경우에만 HTTP 업스트림을 http://127.0.0.1:8787로 설정합니다. 그렇지 않으면 데스크탑 앱에 표시된 포트로 교체하십시오. 프록시가 컨테이너에서 실행되는 경우 자체 127.0.0.1은 다른 네트워크 네임스페이스일 수 있습니다.

확인: 터널은 HTTP 포트를 공용 인터넷에 직접 노출하지 않고도 이 컴퓨터의 게이트웨이에 연결할 수 있습니다.

02
데스크탑 앱

게이트웨이를 저장하고 시작합니다. LAN 및 로컬 브라우저 액세스는 동일한 컴퓨터 터널에 대해 꺼진 상태로 유지될 수 있습니다. 루프백 업스트림은 구성된 공용 호스트를 통해서만 사용할 수 있습니다.

03
프록시 → 앱 → 전화

헤더를 보존하고 각 레이어를 확인합니다.

원래 공용 호스트(사용자 정의 포트 포함), 원본, 쿠키 및 X-CSRF-Token을 보존합니다. Nginx에서는 $http_host가 :8443을 유지합니다. $host가 이를 삭제할 수 있습니다. 캐싱 및 응답 버퍼링을 비활성화합니다. 스트리밍, 긴 요청 및 필요한 업로드/다운로드 크기를 허용합니다. Bridge는 HTTP 긴 폴링 또는 SSE를 사용합니다. WebSocket 업그레이드 지원만으로는 충분하지 않습니다.

앱에서 수정된 항목 확인을 선택합니다. 자격 증명이 필요 없는 HTTPS 프로브를 만들고 인증서와 현재 게이트웨이 인스턴스의 유효성을 검사하며 절대 리디렉션을 따르지 않습니다. 그런 다음 전화 모바일 데이터를 통해 로그인, 채팅 및 파일을 테스트합니다. QR 로그인은 주소가 현재 게이트웨이에 도달한 경우에만 발급됩니다.

다른 NAS 또는 서버의 프록시는 이 컴퓨터의 루프백이 아닌 연결 가능한 컴퓨터 LAN 주소와 함께 고급 NAS 설정을 사용해야 합니다.

NAS / 기존 프록시: 연결 가능한 네트워크 재사용

고급 설정에는 DNS, HTTPS, SSH, 서버 또는 NAS 관리에 대한 관련 지식이 필요합니다. 명령 및 구성은 참조용일 뿐이며 사용자 환경에 적합하지 않을 수 있습니다. 사용하기 전에 이를 검토하고 데이터를 백업하고 필요한 승인을 얻으십시오. 귀하는 이러한 예제를 사용, 수정 또는 실행하는 데 따른 위험을 감수합니다. 해당 법률이 허용하는 최대 범위 내에서 작성자와 기여자는 합법적으로 제외되거나 제한될 수 없는 책임을 제외하고 결과적인 데이터 손실, 서비스 중단, 보안 사고, 비용 또는 기타 손실에 대해 책임을 지지 않습니다.

공용 HTTPS 항목과 업무용 컴퓨터 게이트웨이에 대한 NAS 연결 가능성이 필요합니다.

모든 도메인, IP 및 사용자 이름은 예시입니다. 이를 자신의 값으로 바꾸십시오. try2love.com은 호스팅된 데모가 아닙니다.

02
DNS, 라우터 및 NAS 대시보드

NAS 공개 HTTPS 항목 준비

유효한 일치 인증서와 HTTP에서 HTTPS로 리디렉션되는 전용 호스트 이름을 사용하세요. 기존 공개 항목을 재사용합니다. 그렇지 않은 경우 먼저 공개 IP 가용성, ISP 인바운드 제한 및 라우터 전달 요구 사항을 확인하세요.

NAS 항목을 직접 노출하는 경우 필요한 HTTPS 포트만 해당 프록시로 전달하세요. 인증서 검증 방법에 HTTP가 필요한 경우 포트 80을 준비하십시오. 컴퓨터 포트 8787 또는 내부 릴레이 포트 18787을 노출하지 마십시오. 일반적으로 라우터 전달만으로는 CGNAT 또는 캠퍼스 개인 네트워크를 극복할 수 없습니다.

확인: 모바일 데이터의 전화는 유효한 인증서를 사용하여 NAS HTTPS 호스트 이름에 연결할 수 있습니다.

Docker 릴레이는 언제 필요합니까?

NAS가 컴퓨터에 직접 프록시할 수 있는 경우 Docker 릴레이가 필요하지 않습니다. 중간 HTTP 릴레이가 실제로 필요한 경우에만 내보낸 NAS 번들을 사용하십시오.

컨테이너는 HTTP 릴레이입니다. NAS 인증서 또는 공용 HTTPS를 대체하지 않습니다. 호스트 수준 프록시는 http://127.0.0.1:18787.를 사용할 수 있습니다. 외부 프록시가 컨테이너화된 경우 127.0.0.1은 해당 컨테이너를 참조합니다. 번들에 설명된 대로 제한된 액세스로 연결 가능한 NAS 주소를 구성합니다.

권한 있는 사용자는 Docker 작업을 수행합니다. Compose 구성을 확인하기 전에 내보낸 지침을 읽고 포트와 네트워킹을 확인하세요. 이 가이드와 관련 없는 컨테이너를 수정하거나 내부 포트를 노출하지 마세요.
