# Agent Note: 클라이언트 상태 읽기로 시작 잠금 방지

Status: implemented

## 문제

Windows 설치 패키지가 승인되고 인증되었습니다. `GET /api/clients` 테스트 종료 이후 12 두 번째 읽기 기간; 게이트웨이가 응답하는 동안 클라이언트 연결 끊김이 발생했습니다. 이 요청은 클라이언트 시작, 계정 확인 및 기본 프로세스 확인과 공유됩니다. `client_lock`，콜드 스타트는 긴 작업 뒤에 대기하게 됩니다. 하나의 Windows 프로세스 목록은 약 1초 만에 읽혀지므로 이것이 전체 시간 초과의 유일한 원인이라고 가정할 수는 없습니다.。

## 결정

`GET /api/clients` 기다리지 않고 현재 캐시 읽기만 시도합니다. 캐시가 무효화되거나 시작, 계정 또는 수명 주기 작업에 의해 잠금이 유지되면 마지막 전체 디스플레이 스냅샷이 즉시 반환됩니다. 처음으로 스냅샷이 없으면 빈 목록을 반환하고 다음으로 끝납니다. `pending: true` 결과가 여전히 백그라운드에서 생성되고 있음을 분명히 하십시오. 백그라운드에서 솔로 비행을 새로 고치고 원본을 호출하세요. `clients(refresh=True)`，완료된 요청은 전체 상태를 반환하고 `pending: false`。백엔드를 제공하지 못했습니다. `refreshError`，그리고 다음 새로 고침을 허용하기 전에 2초 정도 기다리십시오. 닫힌 관리자는 새로 고침을 시작하지 않으며 백그라운드 늦은 스냅샷을 게시하지 않습니다.。

Web 에서 `pending: true` 현재 목록, 선택 및 작업 결과 알 수 없는 태그는 이때 유지되며 기존 2초 빠른 폴링이 재사용됩니다. 완전한 결과만이 상태 적용 및 작업 결과 검증에 참여합니다. 디스플레이 스냅샷은 시작, 중지, 종료, 계정 전환 또는 기타 쓰기 작업에 대한 보안 판단에 사용되지 않습니다. 이러한 경로는 원래 잠금, 실시간 확인 및 원자 규칙을 계속 사용합니다.。

## 기존 메모 감사

숨겨진 파일을 사용하여 검색된 활성 노트。`quiet-client-list-status` 및 `shared-client-list-refresh` 채팅 목록과 관련되며 이 애플리케이션의 상태를 결정하지 않습니다. GET 잠금 및 새로 고침 의미; 수정이 필요하지 않습니다。

## 대안

연장하다 Web 또는 승인 스크립트의 읽기 시간 초과는 느린 시작을 수용할 수 있지만 여전히 긴 잠금을 위해 읽기 전용 요청을 대기열에 남겨두고 콜드 시작 인터페이스가 제때에 상태를 알 수 없습니다. 기존 것을 직접 넣어 15 읽기 속도를 높이기 위해 모든 경로에 노출 캐싱이 사용되지만 프로세스 및 계정 상태를 결정하기 위해 쓰기가 이에 의존하는 경우 실시간 확인 요구 사항을 위반합니다.。

## 영향

GET 새로 고치는 동안 이전 전체 스냅샷이 표시될 수 있습니다.；`pending` 스냅샷이 새 상태로 확인될 수 없음을 나타냅니다. 첫 번째 읽기에는 일시적으로 클라이언트 행이 없을 수 있습니다.，Web 이는 사용자가 앱을 닫는 것으로 해석되어서는 안 됩니다. 직접 회귀에는 장기 잠금 점유, 단독 새로 고침, 완전한 상태 복구, 백그라운드 예외 후 제어된 재시도, 경계 닫기 및 쓰기 작업이 여전히 실시간으로 확인되며 Web 선택의 유지 및 알려지지 않은 결과. 현실 Windows 새 테스트 패키지에서 게이트웨이 대기 시간을 다시 확인해야 합니다.。
