# Agent Note: 네이티브 CLI 명시적으로 다시 연결하기 전에 응답하지 않는 프록시 연결을 복구합니다.

Status: implemented

## 문제

게이트웨이로 예약됨 app-server proxy 프로세스가 여전히 살아 있을 수 있지만 더 이상 응답을 읽지 않습니다. 기존의 connect 다음을 사용하는 프로세스만 확인합니다. initialize 결과적으로 사용자는 계속을 다시 클릭하고 여전히 동일한 연결을 사용합니다.，thread/loaded/list 시간 초과 후 복구 경로 없음。

Windows Test 8788 고정의 SSH 계속하면 샘플 반환 409，기다리다 15044ms；동시에 독립적인 신규 에이전트를 찾을 수 있습니다. 16ms 같은 원어민을 읽어보세요 0.160 세션의 전체 3라운드. 이는 새 연결이 대상을 읽을 수 있지만 이전 게이트웨이가 중단된 구체적인 이유를 아직 찾지 못했음을 나타냅니다. RPC，이를 토대로 현장의 근본 원인이 확인됐다고는 할 수 없다.。

## 결정

명시적으로 연결만 되어 있고 아직 전송되지 않았습니다. thread/resume 처음으로 loaded 확인이 발생합니다. AppServerReadTimeout , 현재 에이전트를 한 번 교체하십시오. 프로세스 생성별 검사를 해제합니다. 오래된 구독을 정리하고 새 구독으로 교체하세요. connect 기존에서 connect_lock 연속물. 통화만 다시 연결 client.connect，떠나지 않고 시작하다 daemon 의 fallback。새로운 initialize 주어진 것과 일치해야합니다 CODEX_HOME，그런 다음 다시 읽으세요 loaded 기본 세션 ID, 최종적으로 한 번 전송이 허용됨 resume。

낮은 수준의 읽기, 수동적 관찰, 계정 유휴 확인, 모델 디렉터리 불투명 연결 변경. 쓰기 대기 실패가 남아 있음 AppServerUnknownResult，재생 없음; 두번째 loaded 시간 초과로 인해 현재 연결이 종료됩니다. 닫힌 것은 공유된 기본 서비스나 원래 작업이 아닌 게이트웨이 자체 바이트 프록시입니다.。

## 대안

에서 loaded_threads 기본 자동 재연결은 여러 읽기 항목에 재사용될 수 있지만 observe 이전 프로세스 ID는 기본 작업에 바인딩되었습니다. 투명한 교체는 새로운 프로세스 ID를 우회합니다. home 확인하고 이전 콜백이 실수로 구독을 새로 고치도록 하여 명시적 연결 전에만 처리되도록 합니다.。

공유 다시 시작 daemon 전체 서비스를 복원할 수 있지만 독립적인 읽기가 성공하면 다른 기본 작업이 영향을 받습니다. 다시 시작할 근거나 필요성이 없습니다. 읽기당 제한 시간을 연장해도 유지된 오래된 에이전트가 수정되지 않습니다.。

## 검증

현실 WebSocket/원본의 파이프 클램프 HEAD 의 attach 분석법의 안정적인 재현성 loaded 시간 초과; 현재 구현은 프록시를 교체한 후에만 재정의됩니다. resume 한 번, 다른 home 에서 resume 이전에 거부되었으며 두 번째 시간 초과 이후에는 다시 연결되지 않으며 시작되지 않습니다. daemon，동시에 새로운 join 이전 구독이 정리될 때까지 기다립니다. 기본 추가 확인 읽기 전용 시간 제한은 자체적으로 다시 연결되지 않으며 알 수 없는 원본 쓰기는 테스트를 재생하지 않고 유지됩니다. 위의 합계 11 항목이 통과되었습니다. 결정된 SSH 샘플에 대한 새로운 프로그램의 현장 승인은 아직 수행되지 않았습니다. 픽스처는 기본 서비스가 아니며 실제 테스트 결론입니다.。

## 영향

일반 연결에서는 읽기가 증가하지 않습니다. 비정상적인 연결은 최대 하나의 프록시 연결을 추가할 수 있으며 loaded 확인하다; 원래 읽기 예산은 단축되지 않았습니다. 로컬 통합, 계정 변경 없음、provider、원주민 역사 및 세션 ID。
