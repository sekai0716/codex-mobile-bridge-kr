# Agent Note: Webhook 서비스 사전 설정, 서명 및 성공 결정

Status: implemented

## 문제

초판 유니버설 Webhook ～에 의해 HTTP 2xx 수신 성공으로 판단되며 Feishu의 메시지 구조와 서비스 반환 코드는 다루지 않습니다. 기본 템플릿으로 테스트할 때 사용자에게 알림이 표시되지 않습니다. 사용자 인증을 통해 동일한 임시 로봇과 비교: 일반적인 기본 구조를 얻습니다. HTTP 200 / code 19002；Feishu 텍스트 구조를 얻습니다. HTTP 200 / code 0。일반 기본 수신기의 유효성을 검사하는 것만으로는 타사 프로토콜 호환성이 입증되지 않습니다.。

## 결정

구성에 자동 인식 및 범용 추가 Webhook、페이슈, 딩톡、Discord、Telegram 프로토콜 선택. 각 공식 호스트와 해당 전송 경로를 자동으로 식별하고 제한합니다. 명시적인 서비스 옵션에는 사용자가 만든 적응 입구가 포함됩니다. 서비스 기본 템플릿은 수정되지 않은 범용 기본 템플릿을 대체하며 기존 사용자 지정 템플릿은 유지됩니다. 기본 템플릿은 백엔드, 데스크톱 및 Web/휴대폰은 동일한 정의를 공유합니다. 프런트 엔드는 선택한 템플릿을 명시적으로 채택하기 위한 항목 및 자리 표시자 설명을 제공하고 상태를 읽을 때 사용되는 실제 템플릿을 표시합니다. 수정되지 않은 유효한 템플릿이 반환되어 저장되면 자동 템플릿이 일반 저장 중에 실수로 사용자 정의 텍스트로 변경되는 것을 방지하기 위해 원래 기본 템플릿 태그가 계속 유지됩니다.。

Feishu는 제한된 방식으로 결과를 보냅니다. JSON 응답에서 비즈니스 반환 코드를 판단하고 HTTP 200 메시지를 받는 것과 똑같습니다. 딩톡 사용 errcode，Telegram 엄격한 부울 사용 ok；Discord 힘 wait=true，나머지 쿼리 매개변수를 유지하면서 생성된 메시지가 반환되도록 요청합니다. 오류 코드는 제어 프롬프트에 매핑되며 수신 측의 모든 텍스트와 예외는 직접 에코될 수 없습니다. 명시적 범용 모드는 기존을 유지합니다. HTTP 2xx 의미론. Feishu 텍스트 컬렉션 20 KiB 한계；Discord 문자 길이: 2000 성격，Telegram 이하 4096 문자, 사용자 알림을 자르지 않고 오버런 거부。

선택적 서명은 개인 키 필드를 사용합니다. 각 전송은 초 단위의 타임스탬프, 개행 문자 및 키로 구성됩니다. HMAC-SHA256 의 key，빈 메시지에 대한 다이제스트를 계산하고 진행합니다. Base64 다음으로 인코딩 JSON 최상위 수준 timestamp/sign。이 알고리즘은 다음을 기반으로 합니다.[Feishu 공식 로봇 문서](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)기본으로 적용할 수 없으며 일반적인 경우에는 적용할 수 없습니다.“조표 요청 본문”연산. 재시도는 이벤트 ID를 유지하지만 타임스탬프와 서명을 새로 고칩니다.。

DingTalk 서명은 다른 알고리즘입니다. secret ～을 위한 HMAC-SHA256 key，밀리초 타임스탬프, 개행 및 secret 다음으로 구성된 메시지 계산 요약，Base64 뒤에 넣다 URL 코딩된 sign 매개변수；timestamp/sign 매번 재생성。[DingTalk 공식 안전 지침](https://open.dingtalk.com/document/robots/customize-robot-security-settings)그 기초입니다. Feishu의 빈 메시지 서명 알고리즘은 재사용할 수 없습니다.。

키는 로컬 비공개 알림 구성에만 존재합니다.，GET、데스크탑 snapshot 로그나 로그가 모두 에코되지 않습니다. 빈 입력은 동일한 대상의 값만 유지합니다. 대상이나 프로토콜을 변경해도 이전 키가 자동으로 사용되지 않습니다. 서명이 활성화되었지만 키가 누락된 경우 저장을 거부합니다./보내다. 프로토콜, 서명 스위치 및 키 다이제스트는 ID 전달에 관여하여 이전 재시도가 다른 보안 구성을 상속하지 못하도록 합니다. 원본인증、CSRF、리디렉션, 중복 제거 및 알림 정책 금지는 변경되지 않습니다.。

비밀번호 등 저장된 수신 주소를 사용자에게 적극적으로 확인하도록 요청합니다. 일반 구성 GET/snapshot 계속 둔감화；Web 전용, 인증 및 합격 CSRF 확인됨 POST 얻다 URL，응답은 캐시되지 않습니다. 데스크톱은 기존 개인을 통과합니다. read-credentials IPC 의 webhook 하위 항목을 얻습니다. 이 항목은 요청 헤더나 서명 키가 아닌 주소만 반환합니다. 완전히 사전 로드되지 않음 URL，보기 작업은 수정 사항으로 처리되지 않습니다. 늦은 읽기는 새로운 편집 내용을 덮어쓸 수 없으며 공개된 주소는 닫은 후에 보존되지 않습니다.。

## 관련 결정

찾다 proposed、implemented ～에 Webhook 결정, 유일한 직접적인 타격은[만능인 Webhook 알림 채널](../feature/2026-10-21-custom-webhook-notifications.md)：부분적으로 중복되고 유지되며 상호 연결됩니다. 이 결정은 서비스 계약, 동적 서명, 비즈니스 응답 및 수신 주소에 대한 활성 보기의 경계를 대체합니다. 삭제하거나 거부해야 할 유사한 제안이 없습니다.。

## 대안

사용자가 Feishu 템플릿을 수동으로 입력하도록 하는 것만으로 메시지 구조를 복구할 수 있지만 서명 및 문제 해결은 불가능합니다. HTTP 200 허위 경보는 이 요구 사항을 충족할 수 없습니다. 사용자는 일반적으로 사용되는 서비스에 대해 편집 가능한 사전 설정을 더욱 요구하고 있으므로 명확하게 나열된 서비스 계약을 추가하는 동안 일반 사용자 정의 모드는 유지됩니다. 타사 응답을 직접 에코하면 더 많은 진단이 제공될 수 있지만 타사에서 자격 증명을 반영하고 대신 오류 코드를 통해 제어된 프롬프트를 제공할 수 있습니다. 모든 공급업체에 대해 실행 가능한 서명 스크립트를 추가하는 것이 더 일반적이지만 이는 범위를 벗어나 실행 영역을 확장합니다. 이번 라운드에서는 Feishu 및 DingTalk 표준 서명만 구현합니다.。

## 검증

알림이 통과되었습니다./데스크탑 Python 70 아이템, 데스크탑/Web JS 118 아이템, 인증/CSRF HTTP 3 아이템, 그리고 Chromium 390 px 모바일 레이아웃 24 개、1200 px 데스크탑 인터페이스 22 목. 수락에는 기본 형식 마이그레이션, 사용자 정의 템플릿 보호, 두 서명의 독립적 계산 및 키 읽기가 포함됩니다./바꾸다/명확하게, 적극적으로 보기 URL 접근 제어、HTTP 200 비즈니스 실패, 전류 제한 및 알 수 없는 응답, 두 번의 테스트 진입 및 기존 알림의 회귀. 실제 로봇 결과와 각 플랫폼의 설치 기록은 로컬 승인 디렉터리에 보관됩니다. 소스 코드 테스트 또는 비즈니스 코드의 성공 여부는 사용자가 실제로 메시지를 받았는지 확인하는 것을 대체할 수 없습니다. 사용자가 실제 Feishu 문자 테스트 메시지 수신을 확인했습니다. 프로토콜 시뮬레이션 결과와 다른 서비스의 실제 수신 확인은 별도로 보고됩니다.。

## 영향

새로운 구성은 기존 구성과 호환됩니다. Webhook 데이터, 변경되지 않음 App 버전 또는 휴대폰 바인딩. 서명 확인은 선택 사항 설정이며 로봇 측 스위치와 일치해야 합니다. 키워드와 IP 화이트리스트는 여전히 로봇 측에서 유지 관리됩니다.。Telegram 본문에 꼭 입력해야 할 사항 chat_id；Discord 기본적으로 구문 분석되지 않음 @ 상기시키다. 실패한 재시도는 불확실한 시간 초과 후에도 다시 전달될 수 있습니다. 다른 플랫폼의 동적 서명은 이 문서의 범위에 포함되지 않습니다.。
