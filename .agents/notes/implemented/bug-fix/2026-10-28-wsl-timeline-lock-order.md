# Agent Note: WSL 타임라인 읽기에 대한 잠금 순서

Status: implemented

## 문제

Windows Test 실측중，Codex WSL 대략적인 목록 0.7 초 단위로 반환되지만 동일한 세션 세부정보가 연속으로 두 번 초과됩니다. 40 두번째. 독립형 읽기 전용 프로브는 기본 서비스에 연결됩니다. 0.6 초, 스레드 상태는 대략입니다. 0.02 몇 초 안에 돌아옵니다. 소스코드 분리 WslEntry 첫 번째 보기: 0.34 몇 초 안에 반환되어 연결됩니다. 현장에서 PID 41632 의 py-spy 스레드 스택이 추가로 확인됩니다.：`timeline_read → view → _queue` 쓰기 게이트를 기다리는 중，`activate` 쓰기 게이트가 유지되고 세션 조건 잠금을 기다리고 있습니다. 백그라운드 새로 고침 및 이벤트 스레드도 차단됩니다. 획득에는 호출 스택만 포함되며 로컬 변수나 메모리 덤프는 포함되지 않습니다.。

코드에 재현 가능한 잠금 순서 충돌이 있습니다.：`timeline_read()` 잡고 있다 `session.condition` 호출되는 경우 `view()`；후자는 큐 및 커밋 영수증 읽기를 통해 얻습니다. `write_lock`。쓰기 경로가 먼저 유지됩니다. `write_lock`，그런 다음 동시성 중에 서로 기다릴 수 있도록 세션 상태를 업데이트합니다. 이 잠금 시퀀스는 이전 버전에도 존재합니다. 새 버전에서 실제 측정을 통해 실행되었다고 해서 이번 새로운 기능을 통해 도입되었다고 단정할 수는 없습니다.。

## 결정

타임라인은 먼저 세션 조건 잠금 외부에서 읽기 전용 보기를 얻은 다음 조건 잠금을 유지하여 프로젝션을 업데이트하고 페이징을 읽습니다. 세션 상태 잠금을 유지하는 동안 쓰기 게이트를 기다리지 않습니다. 더 일찍 촬영하고 나중에 도착하는 스냅샷은 게시된 새 시퀀스 투영을 덮어쓰면 안 됩니다. 업데이트는 현재 타임라인 순서보다 작지 않은 스냅샷만 허용합니다.。

쓰기 뮤텍스, 비활성화된 대기, 작업 확인 및 기본 소유권 확인은 그대로 유지됩니다. 뷰를 읽어도 언로드된 세션이 복원되지 않으며 모델 작업이 시작되지 않습니다. 이 수정 사항은 반복되는 잠금 순서 결함을 해결합니다.；Windows 패키지 변경 후 원본 세션 검증은 테스트 기록에서 확인할 수 있습니다. 이를 기반으로 모든 과거 세션을 복원할 수 있다고 주장할 수는 없습니다.。

## 대안

- 연장하다 HTTP 시간 초과 또는 반복적인 재연결은 상호 대기를 완화할 수 없으며 정지 요청을 증가시킵니다.。
- 대기열 읽기에 대한 쓰기 잠금을 제거하면 이 대기를 우회할 수 있지만 영수증 읽기, 쓰기 및 비활성화 간의 기존 계약이 파괴됩니다.。
- 전체 타임라인 프로세스를 쓰기 게이트에 넣으면 잠금 시퀀스의 일부를 통합할 수 있지만 쓰기 중요 섹션에 뷰 어셈블리 및 기타 읽기가 포함됩니다. 여기서는 더 작은 스냅샷 경계 조정이 사용되며 시퀀스가 ​​뒤로 이동하지 않는지 확인됩니다.。

## 영향

타임라인은 더 이상 작성자가 승인을 기다리는 동안 세션 상태 잠금을 획득하는 것을 방지하지 않습니다. 스냅샷 읽기는 더 이상 프로젝션 업데이트와 동일한 중요 섹션에 있지 않으므로 지연된 이전 스냅샷은 거부해야 합니다. 인터페이스 리소스, 계정 구성, 기본 권한 및 지속성 형식은 변경되지 않습니다.。

Claude WSL 독립적으로 판단해야 합니다. 이번 라운드에서 실제로 복구 가능한 샘플은 다음과 같습니다. 6.7 기본 초기화는 몇 초 내에 완료되었으며 모델 메시지가 전송되지 않았습니다. 다른 기록 샘플은 원래 권한 모드를 확인할 수 없어 기존 사전 확인에 의해 거부되었습니다. 둘 다 귀속될 수 없음 Codex 권한 추측으로는 타임라인 잠금을 해제할 수 없습니다.。
