# Agent Note: CLI 동일한 기본 구성을 따르는 계정 및 액세스

Status: implemented

## 문제

원래 도구는 동일합니다. CODEX_HOME 계정 업데이트、API 주사 또는 제공자 후, 실행 CLI 원래 캐시와 클라이언트 구성을 계속 사용할 수 있습니다. 현재 디스크 콘텐츠를 읽거나 기본 계정 유형이 동일한 것을 확인한다고 해서 동기화되었음을 증명하는 것은 아닙니다. 사용자가 명시적으로 새 작업을 계속하거나 시작하는 경우 효과적인 기본 액세스를 먼저 사용해야 합니다. 재구성이 필요할 때 안전하게 기다리세요. 다른 구성이나 게이트웨이 프로세스의 계정은 새로운 소스로 사용할 수 없습니다.。

## 결정

로컬 머신 CLI 소스의 명시적 연속은 새 실행 항목으로 원래 호스트를 확인합니다.、home、실행 생성, 현재 구성 및 저장된 세션 ID。APP 소스 및 IDE 기존 액세스 경계는 변경되지 않습니다. 읽기 기록이나 알림은 유지 관리를 트리거하지 않습니다. 독립적인 로컬 구성은 자체 기본 계정만 따릅니다.，SSH 및 WSL 로컬 계좌를 빌리지 마세요. 실행 중인 작업은 원래 연결을 따라 중지 및 승인되며 비동기 질문 카드 응답에는 원래 요청 및 콘텐츠를 다시 확인해야 합니다. 명시적으로 승인된 이전 대기열 작업은 원래 대기열에서 계속 완료되며 새 계정으로 이전되거나 재발행되지 않습니다. 새로운 대기열 및 보충은 실제 파견 전에 새로운 액세스를 확인하며 작업이 유휴 상태가 된 직후에 건너뛰지 않습니다. 새 요청이 발견되고 액세스가 아직 동기화되지 않은 경우 해당 요청은 전송되지 않은 상태로 유지되며 전송 원장에 초안을 추가하지 않습니다.。

검증된 것과 동일 home 이 세대의 기본 캐시에서 파일 계정을 사용한 경우 파일을 변경하거나 다시 빌드하지 않고 직접 계속됩니다.。API 실제 캐시된 자격 증명 비교，ChatGPT 기본 로그인 계정과 사용자 ID 비교；`getAuthStatus` 인증 데이터는 메모리에서만 비교되며 오류 출력에는 인증 값이 포함되지 않습니다. 게이트웨이에 메모리 기준이 없으면 동일한 세대의 서비스가 시작된 후 파일이 변경되는 것도 변경의 증거입니다. 확인이 실패하면 이전 캐시는 새 작업을 전달하는 데 사용되지 않습니다. 캐시는 그대로 유지됩니다 ID 액세스 정의가 변경되거나 기본적으로 지원되는 공급자가 전환되어 재구축되어야 하는 경우[원래 유휴 업무](2026-11-11-cli-recovery-waits-for-idle.md)，배경은 계속해서 대화를 시작하기만 하고 메시지를 보내지는 않습니다. 이전 대상이 기다리는 동안 인증 또는 구성이 다시 변경되면 이전 트랜잭션이 무효화됩니다. 다음번에는 최근에 확인된 구성에 따라 명시적으로 계속해서 다시 입력해야 합니다. 중복 종료 또는 알 수 없는 쓰기 없음。

원본을 변경하지 않고 다시 빌드 auth/config，이것만 사용하세요 home 게이트웨이의 기본값을 사용하는 대신 검증된 파일 인증 또는 기본 서비스 검증 가능한 주입 변수. 시작 시 파일 인증을 지우면 덮어쓰게 됩니다. OPENAI/CODEX 주사하다; 명백한 provider 환경 변수는 동일한 이전 세대에서 제공하는 값만 취하고, 누락된 경우 거부됩니다. 성공적으로 해제된 원본 세션은 동일하게 사용할 수 있습니다. provider ID、새 파일 인증에서 정상적인 콜드 연결을 확인할 수 있습니다. 원본 릴리스 생성, 작업 및 구성 요약이 유지되며 원본은 시작 전에 기록됩니다. `starting` 영수증을 반환하고 활성화 후 새 인증서를 확인하십시오. 검증할 수 없는 쓰기, 다른 공급자 또는 기타 구성은 이전 자격 증명을 차용하지 않고도 계속 시작됩니다.。

Codex 0.164.0 인증된 네이티브 감기 지원 `thread/resume` provider override；[0.167.0 기본 액세스](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/app-server/README.md#model-provider-admission)저장 및 현재 요청 provider ID 인터페이스가 여전히 `modelProvider` 필드。0.167 예정된 재구축은 수행되지 않습니다. 토종의 `modelProviderMismatch` 구조화된 읽기 전용을 유지하는 이유는 원본 도구에서 원본 공급자를 선택할 수 있고 기록 및 전송되지 않은 콘텐츠가 유지되기 때문입니다. 게이트웨이는 기본 원장을 수정하지 않고 별칭을 사용하여 우회하지 않으며 사용자를 위한 새 채팅을 생성하지 않습니다. 같은 ID 인증 또는 엔드포인트 변경이 계속 이어질 수 있습니다.。

## 대안

`account/login/start(apiKey)` 기본 캐시를 업데이트할 수 있지만 공유 자격 증명을 쓰고 원래 로그인을 취소할 수도 있습니다. 예약해 두세요[명시적으로 선택된 관리 경로 API 동기식](../bug-fix/2026-11-10-managed-cli-auth-sync.md)，외부 인증을 자동으로 무시하지 마세요.。`refreshToken` 캐시된 내용을 다시 읽지 않음 API Key；통화가 존재하지 않습니다 reload RPC 작동한다는 보장은 없습니다. 세션 기록을 자동으로 또는 자동으로 수정 fork 기본 입학을 동일하게 유지할 수 없습니다 ID，따라서 사용되지 않음。

## 검증

124 항목 복구, 계정 동기화 및 릴리스 지정 회귀가 통과되었습니다. 이미 유효한 인증서를 덮어쓰고 다시 작성하지 않음、A→B 보류 중이며 원본 초안이 전송되지 않았습니다.、B 기다리는 동안 C 오래된 거래를 무효화하고 실제 거래로 만들기 RPC 오류 구조를 읽기 전용으로 변환하여 인증 오류가 유출되지 않으며, 실행 중인 작업을 중지 및 동시에 제어합니다. home 주입과 독립/SSH/WSL 격리 및 성공적인 방출 이후에도 동일 provider 새로운 인증 콜드 연결. 인증 감지가 실패하고 게이트웨이에 기준선이 없고 새 게이트웨이가 실행 중일 때 릴리스되었다는 검토 및 수정 사항이 먼저 다시 나타났습니다. queue/steer 검사를 우회합니다. 수리 후 거부되며 기본 배포 및 새 원장이 없습니다. 기존 비동기 응답은 원래 작업에서 계속 수신될 수 있으며, 활성-유휴 인터리빙 중에 새 메시지는 여전히 확인을 우회할 수 없습니다. 또한 6 아이템 네이티브/원격 전송 및 Goal 영향을 받은 회귀 패스。

회귀 분석을 확장하면 실행 중인 상태에서 일반 전송을 위해 이전 파일 인증 장치가 제출되었으며 실행 중인 전송 모드의 거부만 확인할 수 있다는 사실도 발견되었습니다. 수정 후, 시뮬레이션된 게이트웨이는 실행 상태에서 허용하는 보충 모드를 사용하여 동일한 세대의 기본 캐시가 남아 있는 동안 현재 파일 다이제스트를 기록했습니다. 인증 및 검증 후 새로운 보충 자료를 가로채고 전송 원장이 기록되지 않습니다. 이전 작업은 중지되고 원래 연결은 계속 호출됩니다.，CLI 서비스가 종료되지 않았습니다.。

## 영향

동일한 기본 구성은 수동 페이지가 채팅을 활성화하지 않고도 명시적으로 작동할 때 신뢰할 수 있는 현재 액세스를 사용할 수 있습니다. 기본 클라이언트를 다시 생성해야 하는 경우 이 구성 작업이 완료될 때까지 기다려야 합니다. 사용자가 새 메시지를 보내야 합니다. 자동재구축은 정상적으로 종료할 수 있는 능력을 검증한 자에 한합니다. macOS/Linux 로컬 머신 CLI，Windows 출구 통로는 확장되지 않습니다. 시스템 키체인, 알 수 없는 소스, 확인되지 않은 기본 버전 또는 기타 호스트는 파일을 사용할 수 있다고 추론하지 않습니다.。0.167 가로질러 provider ID 동일한 세션 제한은 여전히 ​​업스트림에 의해 결정됩니다. 진실 OAuth 계정 변경, 실제 모델 요청 및 Windows/Linux 패키지 승인은 이 기본 픽스처의 증거가 아닙니다. 이 지점에서는 자동 프록시 따르기 또는 강제 복구가 활성화되지 않습니다.。
