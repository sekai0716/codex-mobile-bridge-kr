# Agent Note: 다수의 Webhook 수신 대상은 이전 구성과 호환됩니다.

Status: implemented

## 문제

Issue #60 초판 Webhook 수신 대상은 하나만 저장됩니다. 사용자는 동시에 다른 서비스에 전송해야 하고, 동일한 서비스의 여러 로봇에 전송해야 하며, 각 대상을 별도로 관리해야 합니다. 이전 구성을 어레이로 직접 변경하면 전달된 이벤트의 채널 ID가 변경되어 기록 알림이 재생되거나 이벤트를 재시도하는 데 혼란을 줄 수 있습니다.。

## 결정

원래 최상위 레이어 유지 `webhookEnabled`、`webhookUrl` 설정 및 `webhook` 채널 아이덴티티 ID ～을 위한 `legacy` 기본 대상. 추가 목표는 비공개로 유지됩니다. `notifications.json` 의 `webhookEndpoints` 배열, 각 항목은 서버에서 생성된 안정적인 값을 갖습니다. `webhookId`、편집 가능 `webhookName` 독립적인 원본 Webhook 구성 필드. 구성되지 않은 기본 대상은 목록에서 빈 행을 차지하지 않습니다. 기본 대상을 삭제하면 해당 필드가 지워지고 다른 대상이 기본 대상으로 승격되지 않습니다. 가장 많이 저장됨 20 추가 목표。

일반 구성 읽기, 데스크톱 스냅샷 및 응답 저장 `webhookEndpoints` 목록은 모두 마스크된 보기를 사용하고 있습니다: 전체 URL、요청 헤더와 서명 키는 반환되지 않습니다. 서비스 도메인 이름, 구성 여부, 선택한 서비스 및 유효한 템플릿이 표시됩니다. 선택한 대상 전체를 읽으려면 주소를 명시적으로 확인하세요. URL。Web 인증으로 패스를 종료하고 CSRF 확인됨 `POST /api/notifications/channels/webhook/url` 들어오는 `webhookId`，개인을 통한 데스크탑 `read-credentials` 작업 읽기; 생략하다 ID 이전 기본 대상만 가리킵니다. 테스트하려면 동일한 키를 누르세요. ID 저장되지 않은 양식 값을 사용하지 않고 저장된 대상을 가리킵니다.。

목표 사용량 추가, 업데이트 또는 삭제 `POST /api/notifications/channels/webhook/endpoints` 또는 데스크톱 개인 `webhook-endpoint` 운영하다, 제출하다 `action: upsert|delete` 그리고 목표 ID；추가시 생략 ID。응답은 감도 줄이기 구성을 반환하고 `selectedWebhookId`，동일한 이름을 가진 대상은 선택된 상태로 유지됩니다. 이전 전체 설정을 저장하면 기본 대상만 계속 업데이트되고 추가 대상은 대체되지 않습니다. 동일한 저장 경로 2개 `notifications.json` 프로세스 내 잠금과 동일한 프로세스 간 파일 잠금을 사용하여 데스크톱을 피하면서 읽기, 확인, 원자 교체 등 전체 읽기 및 쓰기 프로세스를 포괄합니다. worker 게이트웨이 프로세스와 동시 저장 시 다른 대상 손실。

각 알림 소스는 대상 열거를 공유합니다. 채팅, 게이트웨이, 보안 및 계정 경고는 모두 활성화된 대상에 전달됩니다. 추가 대상 사용 `webhook:<webhookId>` 각각 대상 다이제스트, 중복 제거 원장 및 재시도 상태가 포함된 채널 ID 이전 대상은 원본을 계속 사용합니다. `webhook` 마이그레이션 후 재생을 방지하기 위한 ID 및 다이제스트. 전송하고 다시 시도하기 전에 현재 구성을 다시 확인하십시오. 대상을 비활성화, 삭제 또는 교체하면 해당 대상에 대한 이전 재시도만 무효화됩니다. 수신 측에서 처리했지만 게이트웨이 시간 초과로 인해 여전히 중복이 발생할 수 있습니다. 프레스 안정 `event_id` 중복 제거。

## 관련 결정

[사용자 정의 Webhook 알림 채널](2026-10-21-custom-webhook-notifications.md) 원래의 단일 표적 디자인을 기록하면서 표적 수와 신원 규칙을 확장하기로 결정했습니다.。[Webhook 서비스 사전 설정, 서명 및 성공 결정](../bug-fix/2026-10-21-feishu-webhook-delivery.md) 프로토콜 사전 설정, 서명 및 응답 판단은 이 결정의 격리 경계를 변경하지 않고 각 대상에 개별적으로 적용됩니다.。

## 대안

전체를 어레이로 마이그레이션하고 이전 필드를 삭제하면 스토리지 구조가 단순화되지만 이전 채널 ID가 변경되고 기록 알림 재생 위험이 높아집니다. 여러 인터페이스 양식이 단일 대상을 공유하면 이전 봇을 덮어쓰게 됩니다. 추가 대상에 대한 두 번째 대기열 세트를 생성하면 기존 알림 전략 및 원장이 복제됩니다. 원래 채널 메커니즘을 유지하고 안정적인 하위 채널을 새 대상에 할당합니다.。

## 검증

Python 대상 테스트에는 이전 설정 유지, 두 개의 동일한 서비스 대상, 서비스 간 팬아웃, 각 대상 상태 및 재시도 격리, 삭제, 감도 줄이기, 인증 및 CSRF。두 개의 명명된 대상을 동시에 저장하고 기본 대상과 명명된 대상을 동시에 저장하는 이중 프로세스 회귀를 추가했습니다. 복구 전에 쓰기 손실이 발생했으며 프로세스 간 파일 잠금을 사용한 후 통과되었습니다. 이 결정에서는 실제 타사 플랫폼의 최종 배송 또는 설치 패키지 승인이 확인되지 않았습니다.。

## 영향

오래된 저장 Webhook 수동으로 마이그레이션할 필요가 없으며, 완료된 내역은 새로운 대상으로 인해 재발행되지 않습니다. 새로 추가된 각 대상은 독립적인 구성 및 전달 상태를 가지며, 다른 대상은 삭제 후에도 자동으로 변경되지 않습니다. 파일 잠금은 동일한 데이터 디렉터리를 사용하고 잠금을 준수하는 게이트웨이 및 데스크톱 프로세스만 조정합니다. 구성 파일의 외부 직접 편집은 이 동기화 계약에 포함되지 않습니다.。
